## 2. 索引的创建与实验

### 查询、调用链与设计

```sql
SELECT * FROM pms_sku_stock WHERE product_id = 26;
```

后台 `PmsSkuStockServiceImpl.getList → PmsSkuStockMapper.selectByExample → PmsSkuStockMapper.xml` 通过 Example 生成条件。原本机表只有 `PRIMARY(id)`，不能直接按 `product_id` 定位；商品可以对应多个 SKU，因此新增的是非唯一索引。

```sql
ALTER TABLE pms_sku_stock
    ADD INDEX idx_product_id (product_id),
    ALGORITHM=INPLACE, LOCK=NONE;
```

无需改 Java 或 Mapper，优化器会选择访问路径。独立脚本：

- [创建索引](../../document/sql/migrations/20261104_01_sku_product_id_up.sql)
- [回滚索引](../../document/sql/migrations/20261104_01_sku_product_id_down.sql)

原业务表只有 96 行，商品 26 匹配 4 行，不足以验证规模收益。实验在独立库构造 100,000 条 SKU、20,000 个商品，每商品 5 条。

### 查询结果

每组预热 5 次，保留 30 次，计时为同一 MySQL 会话的服务端语句耗时。

| 指标 | 无索引 | 有索引 |
| --- | --- | --- |
| EXPLAIN type / key | ALL / NULL | ref / idx_product_id |
| EXPLAIN 估算 rows | 98,900 | 5 |
| ANALYZE 实际路径 | 全表迭代输出 100,000 行，再筛出 5 行 | 索引查找输出 5 行 |
| 查询中位数 | 18.922375 ms | 0.047250 ms |

该次中位数约快 **400.47 倍**，耗时减少 **99.75%**。只适用于这条查询的模拟数据、单连接热缓存实验，不能推导整个商品模块提升 400 倍。

执行计划要分清：`EXPLAIN rows` 是估算；`EXPLAIN ANALYZE` 会真正执行并提供 actual rows/time/loops。索引输出 5 行不等于只发生 5 次磁盘读取。`SELECT *` 需要完整记录，此二级索引不是覆盖索引，仍有回表成本；小表优化器选择全扫描也可能合理。

### INSERT、DELETE、UPDATE 的影响

使用相同 10 万行的两份隔离表，每类预热 5 轮、测量 15 轮，交替先后顺序。下表包含 JDBC 往返与 COMMIT，不能与上面的服务端 SELECT 耗时直接比较；1000 行操作是一个批量事务。

| 操作 | 无索引中位数 ms | 有索引中位数 ms | 观察 |
| --- | ---: | ---: | --- |
| INSERT 1000 行 | 7.241 | 7.298 | 约慢 0.8% |
| 按主键 DELETE 1000 行 | 5.358 | 5.879 | 约慢 9.7% |
| 按主键 UPDATE stock 1000 行 | 7.316 | 6.029 | 波动，不能归因于该索引 |
| 按主键 UPDATE product_id 1000 行 | 6.185 | 7.249 | 约慢 17.2% |
| 按 product_id UPDATE stock 5 行 | 24.667 | 1.545 | 约快 15.96 倍 |

索引不仅服务于 SELECT：UPDATE/DELETE 的 WHERE 也可用它定位。另一方面，INSERT/DELETE 要维护索引项，修改索引列需要调整索引；按主键只改 stock 不会获得新的定位优势。以上百分比是实测样本，不是固定写入成本。

### 正确性、部署与回滚

真实 MyBatis 验证存在/不存在商品、SKU 编码过滤、count 和主键查询；两份 10 万行数据全部 11 列的规范化 SHA-256 一致，写入恢复后也一致。隔离库实际完成 `up → down → up`，索引为非唯一，EXPLAIN 使用 `idx_product_id`。

项目未引入 Flyway/Liquibase，本次采用手工迁移脚本，未改 `document/sql/mall.sql`。部署步骤：

1. 明确目标 schema，检查 `SELECT DATABASE()`、`SHOW CREATE TABLE`、`SHOW INDEX`，核对版本、备份及执行窗口。
2. 如果已有以 `product_id` 为最左列的等价索引，不重复添加；同名不同定义则先核对。脚本重复执行会失败，不是幂等脚本。
3. 在获准的目标环境执行 up，复核索引、EXPLAIN、查询结果及写延迟。
4. 需要回滚时确认该索引确为本次创建，再执行 down；只撤销索引，不删除业务行。

DDL 隐式提交，不能依靠事务 ROLLBACK 撤销；`LOCK=NONE` 也不代表没有元数据锁或资源开销。**本次没有对业务库执行以上部署步骤。**

## 3. 逻辑删除与物理删除：项目实际采用什么

### 商品主记录采用逻辑删除，依据是实际 UPDATE

`PmsProductController.updateDeleteStatus → PmsProductServiceImpl.updateDeleteStatus → PmsProductMapper.updateByExampleSelective`。

Service 只设置删除标记并按商品 ID 更新，等价 SQL：

```sql
UPDATE pms_product SET delete_status = 1 WHERE id IN (...);
```

不是因为“有 delete_status 字段”才作此判断，而是实际删除入口执行 UPDATE。该入口没有同步删除 SKU、属性值、阶梯价、满减或会员价，也没有同时修改 `publish_status`。接口允许传回 0，因此具备重置删除标记的能力，但不等于已经实现完整的恢复审核、搜索同步与业务恢复流程。

商品编辑 `PmsProductServiceImpl.update()` 中另有物理删除：价格、属性值和关系数据常采用删旧重建，SKU 更新也会删除被移除的记录。这属于编辑维护子数据，不能据此把商品删除入口说成物理删除。

### 删除与下架是两个业务动作

- 下架：`publish_status=0`，表示暂停对外销售，可以重新上架。
- 删除：`delete_status=1`，表示退出正常商品管理/销售范围，保留主数据和历史关联。
- 是否接受新订单要同时检查未删除与已上架；不能用某一个标记替代另一个。
- 已经合法创建并锁库的订单，应按订单状态、支付期限等规则处理，不应因商品后来下架就简单拒绝支付。

### 原实现的问题与尚存边界

| 位置 | 源码或实验结论 | 当前状态 |
| --- | --- | --- |
| 后台商品列表、简单列表 | 显式过滤 `delete_status=0` | 保留 |
| 商城商品搜索 | 检查未删除、已上架 | 保留 |
| 商城商品详情 `PmsPortalProductServiceImpl.detail` | 主键读取，仅判断存在，没有统一检查两种状态 | 本次未改；已知 ID 仍可读取的源码证据 |
| 首页新品/推荐 `HomeDao.xml` | 对商品检查上架，但相关查询未检查商品删除标记 | 本次未改；可能暴露仍上架的已删除商品，未作接口回归 |
| ES 导入 `EsProductDao.xml` | 源数据过滤未删除且已上架 | 状态变更后已有 ES 文档是否及时失效需另查，不能仅凭导入条件保证 |
| 原加购、生成订单链路 | 缺少商品可售性和 SKU 归属校验 | 已复现并修复，见下一节 |

保留关联子表不等于数据残留 Bug：逻辑删除需要恢复和历史查询，子表可以继续保留，也不必机械地全部增加删除标记。关键是对外使用子表时检查主商品资格，并明确历史读取权限。索引、搜索、详情、缓存的状态规则不一致才会造成遗漏；未验证的路径不能直接宣布已经发生线上问题。

### 工程选型原则

| 方案 | 优点 | 代价与适用范围 |
| --- | --- | --- |
| 逻辑删除 | 易恢复，保留关联与历史 | 所有有效数据查询要考虑状态，数据和索引继续增长，适合商品、需恢复的业务记录 |
| 物理删除 | 释放逻辑存储占用，查询无需删除条件 | 恢复依赖备份，须处理引用和审计需求，适合无保留价值的临时数据 |
| 归档后物理删除 | 热表缩小，历史可独立保留 | 需要归档校验、查询入口和保留期限，适合大量历史订单、日志等 |

常见选择：商品通常逻辑删除；订单保留历史和下单快照，后期可归档；购物车允许较短保留并清理失效记录；用户“注销”不能简单等同于改一个删除标记，还要按数据保留要求处理个人信息、匿名化及必要业务记录；日志按类型与期限轮转、归档或清理。

逻辑删除不会自动释放唯一键，也不解除数据库外键关联；恢复可能与新数据冲突。给唯一键简单加一个 0/1 删除标记，也未必支持多条历史重复值。当前 `pms_product` 初始化定义只有主键，不能把其他项目的唯一键冲突说成本项目已发生的问题。状态字段选择性低，不应为了逻辑删除就盲目单独建索引，需结合过滤、排序和执行计划设计。

面试回答应先问：是否需要恢复、是否有历史引用与审计、数据增长多快、个人信息如何保留，再决定逻辑删除、直接清理还是归档；不是“所有业务都逻辑删除”。

## 4. 已实施的业务修复与回归

### 缺陷复现

在 `mall_product_state_order_lab` 中，正常、加入前删除、加入前下架、加入后删除、加入后下架五种情况原先都能加购、建单并继续模拟支付扣库存。购买 2 件时，建单 `stock/lock_stock=10/2`，支付后 `8/0`。这是已落库复现的正确性缺陷，不只是理论推测。

原因：原 `OmsCartItemServiceImpl.add()` 直接写购物车；原 `generateOrder()` 依赖促销查询和可用库存，没有重新核对商品状态。购物车自身的删除标记不能代表主商品可售。前端隐藏商品也不能阻止直接请求或旧购物车下单。

### 最小修复

| 文件 | 修改 |
| --- | --- |
| `mall-portal/.../service/impl/ProductSaleValidator.java` | 新公共组件，批量读取商品/SKU，检查存在性、`delete_status=0`、`publish_status=1` 和 SKU 归属 |
| `mall-portal/.../service/impl/OmsCartItemServiceImpl.java` | 新增和增加数量之前调用校验 |
| `mall-portal/.../service/impl/OmsPortalOrderServiceImpl.java` | 确定当前会员实际选中的购物车，全部校验后用同一批数据计算原促销，之后保留原库存、订单和消息流程 |

两个批量 `id IN (...)` 查询避免逐商品 N+1。任何失效条目导致整单失败，不静默过滤后生成部分订单；实际空购物车也拒绝。`cartIds` 为空时仍保留原来选择当前会员全部购物车条目的语义。

异常复用 `Asserts → ApiException → GlobalExceptionHandler`：参数错误 40001、不存在 40401、状态/归属冲突 40901，并在 `details.reason` 返回具体原因。没有改支付回调、库存扣减或订单状态机。

### 实际回归

新隔离库 `mall_product_state_order_regression_lab` 中 **21 项全部通过，含 18 项拒绝场景**：

| 场景 | 修复后实际结果 |
| --- | --- |
| 正常商品 | 加购、建单、模拟支付成功 |
| 加入前删除 / 下架 | 分别拒绝加购 |
| 加入后、下单前删除 / 下架 | 分别拒绝建单，购物车保留 |
| 商品不存在 / SKU 不存在 / SKU 属于其他商品 | 加购和历史购物车下单均拒绝 |
| 混合正常和已删除 / 已下架商品 | 分别整单拒绝 |
| 商品失效后增加已有购物车数量 | 删除、下架两种均拒绝，原数量不变 |
| 空 SKU / 空购物车 / 无效选中编号 / 其他会员购物车 | 均拒绝 |
| 两个正常商品 | 成功建单，各锁库 2 件，状态校验共 2 条 SQL |
| 合法订单创建锁库后商品下架 | 原支付流程仍可模拟成功，库存 `8/0`、订单状态 1 |

18 项拒绝场景均对请求前后订单、明细、SKU、购物车的全字段排序摘要进行比较，全部不变；写 SQL 为 0，消息替身调用增量为 0，业务异常及 HTTP 状态映射符合预期。原缺陷复现目录 13 个文件摘要未变。

已实际用 Java 17 编译目标、真实 Mapper/XML/MySQL、`SqlSessionTemplate` 和 Spring 事务代理验证。订单接口原有 `@Transactional` 保留，所有业务写入均验证事务活跃；校验异常发生在写入之前。没有运行完整 Maven 多模块构建、完整 Spring Boot/HTTP 鉴权端到端、真实 Redis/MQ/支付或并发测试。

**并发边界未解决：** 普通 SELECT 校验商品后，管理员仍可能提交下架/删除，再由下单事务继续锁 SKU 和建单。可重复读不等于阻止并发状态修改，锁 SKU 也不等于锁商品。本次没有擅自加锁或改变隔离级别，只解决顺序执行中的遗漏。

## 5. 补充实践：编辑详情 JOIN 膨胀

后台 `GET /product/updateInfo/{id}`：`PmsProductController → PmsProductServiceImpl → PmsProductDao.getUpdateInfo → PmsProductDao.xml`。

主商品同时关联 SKU、属性值、会员价、阶梯价、满减五组一对多。高规模组合为 `10 × 8 × 3 × 2 × 2 = 960` 行；LEFT JOIN 子集合为空时按 `max(1,条数)` 计算。索引只能帮助定位，不能消除合法组合产生的行。

MyBatis `resultMap` 根据父子 `<id>` 和 `columnPrefix` 合并重复对象，所以最终可以只返回一个商品，但数据库和 JDBC 仍要处理重复宽行。五个 JOIN 集合不另发 SQL；专题和优选使用 `collection select`，另发两次查询，原方案实际共 3 条。实验拆分方案为商品与分类加七个集合，共 8 条，不是单商品列表 N+1。

原 Mapper 与实验拆分共用相同数据、索引，每组预热 5 轮、测量 30 轮：

| 规模 | 原 JOIN 主查询行数 | 拆分全部查询行数 | 原方案中位数 ms | 拆分中位数 ms |
| --- | ---: | ---: | ---: | ---: |
| 低 | 1 | 10 | 2.531 | 4.297 |
| 中 | 96 | 20 | 7.361 | 3.178 |
| 高 | 960 | 30 | 44.104 | 3.310 |

原方案除主查询外还有 4 行专题/优选数据，全部行数为 5/100/964，不能与拆分行数混用口径。三组商品与七个集合完整字段一致；高组拆分约快 13.32 倍，低组反而因额外往返更慢。

主商品文本在 JOIN 每行重复，拆分只读一次；但本轮没有精确测量网络流量或单独映射耗时。`EXPLAIN ANALYZE` 的服务端时间不等于完整 MyBatis 调用时间，不能把差值全算成对象映射。拆分多条 SELECT 还涉及一致性快照，原方案也有嵌套查询，并非天然全程同一快照。

额外发现原 XML 未投影 `sku_lock_stock`，导致映射值为 null。实验拆分刻意保留这一原行为，没有借性能实验修改正式逻辑。正式 JOIN、映射遗漏均未修复；是否拆分需结合真实关联基数、请求量、网络 RTT 及空集合/快照回归再决定。

上传范围为业务修复代码、索引创建/回滚脚本和去重后的文档。实验源码、造数 SQL、日志、快照和结果文件保持本地，不纳入此次提交；下面只是本地证据目录说明，不是执行入口：

| 本地目录 | 用途 |

| `learning/product/sku-index-task01/` | 迁移回滚、读写和 Mapper 一致性 |

建议按“SQL 如何定位 → 索引的读写代价 → JOIN 中间行与 MyBatis 映射 → 删除后的可售规则 → 服务端事务与并发边界”复习。核心原则是先确认业务结果正确，再在隔离环境测性能，最后区分已验证、已修改与已部署。
